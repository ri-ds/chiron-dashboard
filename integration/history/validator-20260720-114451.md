## How this was checked (methodology)

- **Black-box, public API only.** The validator speaks HTTP the way any external consumer would — no import of Chiron, no DB access, no internals.
- **Expected types come from Chiron's own contract.** Field types are derived from Chiron's DRF serializers + Django models (captured in `specs/inventory.json`). Key v2/v1 endpoints have hand-verified, serializer-accurate contracts in `specs/overrides.json` (strict); the rest use auto-derived contracts that type-check *present* fields and container shape (lenient — so a failure is real).
- **Synthetic data only.** Warehouse subjects are Synthea-style synthetic records; request payloads are synthetic query definitions built from live concept metadata. No real PHI is used or generated.
- **Read-only by default.** GET/HEAD + the non-mutating concept `PUT` run by default; create/update/delete require `--include-writes` / `--include-destructive`.
- **Verdict semantics.** A *type verdict* (pass/fail) is only formed on a 2xx response. `401/403/5xx` = hard fail (should be reachable & healthy); `404`/stateful-`4xx` = *unreached* (needs prior state / not applicable here), reported separately so the pass rate reflects genuine type correctness.
